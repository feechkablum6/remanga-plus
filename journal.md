# Журнал изменений

## 2026-08-24 — remanga.org сменил URL-схему, расширение молча выключилось

**Симптом (жалоба пользователя):** «расширение вообще не работает — тумблер скрытия каталога
не работает, и парсер глав тоже».

**Что оказалось.** Две независимые поломки, обе от изменений на стороне сайта, обе без единой
ошибки в консоли — расширение исправно грузилось и просто не находило то, что искало.

### 1. Читалка переехала на `/content/` — Premium Free не запускался

`isReaderPage` проверял `^/manga/[^/]+/\d+`. Сайт теперь ведёт читателя на
`/content/<dir>/<chapterId>?page=1`, а старый `/manga/<dir>/<chapterId>` остался рабочим
алиасом — по нему же ведут внутренние стрелки «предыдущая/следующая глава» внутри читалки.
Пользователь заходит по `/content/`, `isReaderPage()` возвращает false, и вместе с ней
отключается всё: reader-enhancer, префетч, Premium Free.

Замер на живой платной главе (`solo-leveling_`, том 12 глава 36):

| URL | элементов с `data-rre-*` | панель Premium Free |
|---|---|---|
| `/content/solo-leveling_/211773?page=1` | 3 | нет |
| `/manga/solo-leveling_/211773` | 51 | есть, резолв идёт |

Три уцелевших элемента на `/content/` — это fullscreen-bridge и home-enhancer, которые
работают вне зависимости от маршрута; отсюда и ощущение «расширение вообще мертвое».

Та же схема была зашита ещё в четырёх местах: `content.ts` (метаданные для префетча),
`premium-free.ts` (`extractPathMetadata`), `reader-enhancer.ts`
(`extractPremiumFreeRemangaChapterId` и три селектора `a[href*="/manga/"]` для навигации
по главам).

**Правка.** Новый модуль `src/remanga-routes.ts` — единственный источник правды по схеме URL
(`isReaderPathname`, `matchReaderLocation`, `matchReaderChapterId`, `READER_LINK_SELECTOR`),
все пять мест переведены на него. Тесты — `tests/remanga-routes.test.ts`.

### 2. Каталог в шапке переехал с `/manga` на `/catalog`

Локатор `catalog: a[href="/manga"]` не находил ничего, тумблер выглядел сломанным.
`https://remanga.org/manga` теперь отдаёт 404, живой адрес — `/catalog`.
Остальные девять локаторов шапки проверены на живой странице и целы.

**Правка.** Локатор держит оба href (`/catalog`, затем `/manga`), тест в
`tests/home-enhancer.test.ts` покрывает оба.

### Проверено фактом (Chrome, после reload расширения)

- Главная: ссылка «Каталог» получает `data-rre-home-hidden="catalog"`, высота 0 —
  тумблер пользователя был включён всё это время.
- `/content/<dir>/<chapterId>`: панель Premium Free появляется, резолв уходит на
  parser-server (202 → polling), элементов с `data-rre-*` — 51 вместо 3.
- `npm run check`, 60 тестов (`remanga-routes`, `home-enhancer`, `premium-free`,
  `chapter-prefetch`) — зелёные.

### 3. На VPS отвалился DNS — parser-server не видел ни одного источника

Даже после починки маршрутов главы не находились: панель доходила до «Ни один источник не
содержит эту главу». Локальный parser-server (`PORT=7999`) те же главы находил — значит дело
не в провайдерах, а в сервере.

На VPS `/etc/resolv.conf` указывает только на Google DNS, а он с этой машины недостижим:

| Проверка с VPS | Результат |
|---|---|
| `dig @8.8.8.8 mangabuff.ru` | `communications error … timed out` |
| `dig @1.1.1.1 mangabuff.ru` | `190.115.16.11` |
| `ping 1.1.1.1` | 0% потерь |
| TCP 443 до `190.115.16.11` | открыт |
| `curl https://mangabuff.ru/` | `000` (Resolving timed out) |
| `curl --resolve mangabuff.ru:443:190.115.16.11 …` | `200` |

Сеть исправна, источники VPS не банят — умирал только DNS-резолв, и все провайдеры разом
падали «ошибкой». Симптом маскировался под «источники сломались».

**Правка.** `parser-server/deploy/compose.yaml` — контейнеру задан свой resolver
(`dns: 1.1.1.1, 9.9.9.9`) вместо наследования хостового. Залито на сервер, контейнер пересоздан.

Хостовой `/etc/resolv.conf` намеренно не тронут: он общий для всех проектов на VPS.
Если наружу полезет ещё один контейнер — ему понадобится такой же `dns:`, либо DNS хоста
надо чинить отдельно и осознанно.

### 4. Панель называла «ошибкой» источник, у которого просто нет главы

`mapServerProgressToChips` мапила в `not_found` только `no_match`, а `chapter_not_found`
уезжал в `provider_error`. На живой главе это давало «InkStory — ошибка», «Telemanga — ошибка»
у совершенно здоровых источников, из-за чего рабочая панель выглядела сломанной и мешала
диагностике. Теперь `chapter_not_found` — это «не найдено»; «ошибка» остаётся за настоящими
сбоями. Тесты — `tests/premium-free-progress-chips.test.ts`.

### 5. Источники: Teletype отключён, Usagi починен, Telemanga листает главы

Три правки по итогам разбора, все проверены живыми прогонами против настоящих API.

**Teletype — выведен из резолва.** Домен мёртв: HTTPS не отвечает (`SSL_ERROR_SYSCALL`),
HTTP отдаёт 410/451 Gone. `TeletypeProvider` больше не регистрируется в
`parser-server/src/server.ts`, `teletype` убран из `DEFAULT_PROVIDER_PRIORITY`. Файл провайдера
оставлен на диске с датированной пометкой в шапке. Тумблер Teletype убран и из попапа
расширения (`popup-categories.ts`) — он управлял несуществующим источником; сам ключ настройки
в `settings.ts` сохранён, чтобы сохранённые настройки продолжали мержиться.

Отключение сознательно сделано в одном месте — в списке регистрации. Промежуточный вариант с
`DISABLED_PROVIDERS` внутри `ProviderRegistry.register` убран: реестр, молча выбрасывающий
то, что ему передали, прячет причину от читателя `server.ts`.

**Usagi — починен под новые эндпоинты.** Поиск переехал: `/search?q=` отдаёт 404/302 на пустую
выдачу, рабочий вход — `/search/suggestion?query=` с заголовком `Referer` (200, JSON).
В `readerInit` появился шестой элемент, из-за чего старый regex доставал 0 страниц.
Проверка после правки на `solo_max_level_newbie` («Я единственный новичок максимального уровня»,
алиас «Нуб максимального уровня»): 273 главы, глава 36 — 10 страниц, глава 272 — 89 страниц,
ссылки на картинки живые.

**Telemanga — постраничная догрузка глав.** Раньше запрашивалась одна страница
`offset=0&limit=100`, и главы со 101-й для провайдера не существовали. Теперь страницы идут
`offset=0,100,200…` до `totalChapters` из карточки тайтла, короткой страницы или потолка в
20 страниц (2000 глав). Проверка на живом API: у `nub-maksimalnogo-urovnya` загружается
258 глав вместо 100, максимальный номер — 257.

Тесты: 124 в `parser-server`, 91 во фронте — зелёные.
